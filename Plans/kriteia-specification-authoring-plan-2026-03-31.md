# Kriteia 仕様書策定計画

## 概要
- Kriteia は Noesis の探索能力と Anchor 系の根拠付き受理を統合する AI ネイティブ言語である。
- 候補生成、分岐探索、根拠収集、検証、採否判定を一つの言語制御フローとして仕様化する必要がある。
- 本計画は既存資料から継承できる内容を明示しつつ、仕様書として未確定の事項を整理する。
- 本計画は仕様書本文ではなく、仕様策定を進めるための実行可能な工程を定義する。
- 完成後は、別担当者でも同じ前提で仕様書執筆に着手できる状態を目指す。

## 目的

Kriteia の言語仕様を、構想メモや比較資料ではなく、参照実装、標準ライブラリ設計、利用者教育の基準となる正式仕様書へ落とし込むための策定計画を定義する。特に、Noesis と Anchor 由来の概念を Kriteia の一貫した言語仕様へ統合し、構文、型システム、実行モデル、エラーモデル、標準ライブラリ範囲を段階的に確定する。

本計画における想定読者と主な利用目的は次のとおり。
- 言語設計担当: 概念境界、章構成、用語、非スコープの統制
- 処理系実装担当: 型規則、文法、実行モデル、エラーモデルの実装可能性確認
- 標準ライブラリ設計担当: 組み込み機能と拡張インターフェースの境界整理
- AI 応用設計担当: ユースケース、受理条件、監査可能性の妥当性確認

本計画の直接成果は「仕様書ドラフトを書くための工程定義」であり、各フェーズ終了時点で次フェーズへ進んでよいかを判定できる状態を作ることを成功条件とする。

## スコープ

1. 言語の中核概念の正式定義
   - prompt、claimset、evidence、branch、checkpoint、judge、accept、policy
2. 計算モデルとランタイムの仕様化
   - Plan、Explore、Ground、Accept の四段階状態遷移
   - choice point engine、constraint synthesizer、judge pipeline、acceptance gate
3. 型システムの仕様化
   - semantic type
   - draft 型と accepted 型の分離
   - policy と metric の型上の扱い
4. 文法と構文の仕様化
   - 完全な BNF または EBNF
   - branch、checkpoint、judge、accept の構文規則
5. 第1版標準ライブラリ範囲の確定
   - think、retrieve、judge 系組み込み機能
   - Verifier、Evaluator、Retriever の拡張インターフェース
6. エラーモデルと fallback 戦略の整理

## 非スコープ

1. 参照実装そのものの開発
2. IDE、LSP、デバッガ、プロファイラなどのツールチェーン詳細
3. FFI や他言語連携の完全仕様
4. 分散マルチエージェント実行の完全設計
5. 高度な最適化、JIT、性能チューニング詳細
6. 標準ライブラリ完全版の策定
7. バージョニングと後方互換性の最終方針
8. 学習教材、チュートリアル、教育コンテンツ

## 既存資料から継承できる内容
### 概念
- Noesis 由来の探索、分岐、制約生成、バックトラッキングを継承できる。
- Anchor 系の claim、evidence、judge、accept を継承できる。
- Kriteia 固有の「候補生成から採否判定までを一つのライフサイクルで扱う」という中心思想を継承できる。
- Meaning-Typed IR と Evidence Graph IR の二重構造を継承できる。

### 用語
- prompt、claimset、evidence、branch、checkpoint、judge、accept、policy、accepted artifact は継承可能。
- candidate、grounded、accepted などの状態語彙も継承可能。
- 要確認: semantic type、accepted 型、policy constraint の日本語訳と英語表記の統一。

### 実行モデル
- Plan、Explore、Ground、Accept の四段階実行モデルを継承できる。
- Choice Point Engine、Constraint Synthesizer、Judge Pipeline、Acceptance Gate の責務分割を継承できる。
- 要確認: branch の評価戦略、judge の複合時挙動、rollback の粒度。

### 型システム
- semantic type を中心に据える方向性を継承できる。
- draft 型と accepted 型の分離という発想を継承できる。
- evidence や policy を型システムへ接続する方向性を継承できる。
- 要確認: 型形成規則、subtyping、generic type parameter、effect type の範囲。

### AI ワークフロー
- prompt による候補生成、branch による探索、ground による根拠付け、judge による検証、accept による採用という流れを継承できる。
- 高説明責任 RAG、AI コードレビュー、法務・医療・金融系支援などのユースケースを継承できる。
- fallback と escalation の概念も継承可能だが、仕様化は要確認。

## 不足している論点
| 論点 | 現状 | 仕様化で決めること | 優先度 |
|---|---|---|---|
| branch 構文の完全定義 | width、score by、require の例示はあるが評価規則が未確定 | width の固定か動的か、score 関数の戻り値型、require 失敗時の挙動を決める | 高 |
| checkpoint の副作用管理 | 巻き戻し可能範囲が不明 | DB、ファイル、外部 API をどう扱うか、ネストと復元範囲を決める | 高 |
| policy の言語化 | ReleaseGate 例はあるがポリシー言語の形式がない | policy の BNF、論理結合、停止性、合成ルールを決める | 高 |
| judge の戻り値型 | 構造化失敗情報のイメージはあるが型がない | JudgeResult の型、複数 judge の失敗結合戦略、点数化の規則を定める | 高 |
| accepted 型の意味論 | draft と accepted の区別はあるが形式未定 | draft<T> から accepted<T> への変換規則、公開可能性の意味を定義する | 高 |
| semantic type の形式化 | 概念的記述に留まる | 型形成規則、型検査規則、制約生成の範囲を明示する | 高 |
| evidence graph の永続化 | 監査用途の説明はあるが保存形式が未定 | 実行時保存形式、再検証、監査ログとの関係を整理する | 中 |
| エラーモデル | fallback の例示中心で体系がない | compile-time、runtime、judge failure の分類と回復戦略を決める | 中 |
| 標準ライブラリ境界 | 言語組み込みと stdlib の切り分けが不明 | think、branch、retrieve、judge のどこまでを組み込みとするか決める | 中 |
| 並行実行の扱い | branch が暗黙並列に見えるが正式仕様なし | スケジューリング、キャンセル伝播、リソース制限の方針を定める | 中 |
| 型推論の範囲 | 意味情報は多いが推論アルゴリズムが未定 | 明示注釈の必要範囲、推論失敗時の報告を決める | 中 |
| 将来拡張との接続 | Chord、Lattice、Mosaic との接続は比較止まり | 将来の融合余地を残す設計ポイントを整理する | 低 |

## 仕様策定フェーズ
### フェーズ1: 概念統合と資料精読
- 入力: Kriteia 本体仕様、Kriteia 比較総覧、Noesis、追加の AI ネイティブ言語アイディア、パラダイム分析レポート
- 決定事項: 用語統一、継承対象、資料間の矛盾、未確定論点の優先順位
- 成果物: 用語集、概念マッピング、継承一覧、不足論点テーブル、decision log 初版、open issues log 初版
- レビュー観点: 継承内容が正確か、矛盾抽出に漏れがないか、中心思想が一貫しているか

### フェーズ2: 型システムの仕様化
- 入力: フェーズ1成果物、型に関する既存資料の記述
- 決定事項: semantic type、draft 型、accepted 型、policy と metric の型上の扱い、effect type の範囲
- 成果物: 型システム草案、型形成規則、型推論方針、未解決型論点一覧、decision log 更新版
- レビュー観点: 理論的一貫性、実装可能性、既存概念との整合性

### フェーズ3: 文法と構文の確定
- 入力: フェーズ2成果物、既存コード例
- 決定事項: 字句規則、完全 BNF または EBNF、構文上の優先順位、予約語
- 成果物: grammar spec、構文例集、構文上の曖昧性リスト、decision log 更新版
- レビュー観点: 曖昧性がないか、主要コード例を正しく表現できるか、記法が過度に冗長でないか

### フェーズ4: 実行モデルとランタイム意味論の定義
- 入力: フェーズ2の型システム、フェーズ3の grammar、既存の実行モデル記述
- 決定事項: 四段階状態遷移、choice point engine、constraint synthesizer、judge pipeline、acceptance gate の意味論
- 成果物: semantics spec、状態遷移図、探索戦略仕様、エラーモデル下書き、decision log 更新版、review log 初版
- レビュー観点: 意味論が網羅的か、non-determinism の扱いが明確か、枝刈りが収束性を壊さないか

### フェーズ5: 根拠・検証・受理の仕様化
- 入力: フェーズ4成果物、Anchor 系資料、Kriteia の judge 例
- 決定事項: claimset と evidence の構造、evidence graph、judge の戻り値型、accept 条件、fallback 戦略
- 成果物: grounding/judge/accept 章草案、JudgeResult 定義、監査観点メモ、decision log 更新版、open issues log 更新版
- レビュー観点: 受理条件が明確か、検証失敗の表現が十分か、監査可能性が確保されているか

### フェーズ6: 標準ライブラリ範囲と拡張ポイントの固定
- 入力: フェーズ5成果物、既存ユースケース記述
- 決定事項: think、retrieve、judge 系の標準 API、Verifier/Evaluator/Retriever の拡張インターフェース
- 成果物: stdlib API 草案、拡張ポイント一覧、非スコープ項目整理、decision log 更新版
- レビュー観点: 言語組み込みと stdlib の境界が明確か、拡張しやすい設計か

### フェーズ7: 仕様書ドラフト統合と矛盾排除
- 入力: フェーズ1からフェーズ6の成果物
- 決定事項: 章間参照、図表、用語集、未解決事項の保留先、v1.0 の範囲
- 成果物: 仕様書ドラフト v1.0、矛盾解消ログ、open issues log 更新版、review log 更新版
- レビュー観点: 章間の整合性、説明不足や重複の有無、別担当者が着手可能な粒度か

### フェーズ8: 専門家レビューと最終調整
- 入力: 仕様書ドラフト v1.0、レビューコメント
- 決定事項: 修正反映方針、据え置く論点、将来版へ送る項目
- 成果物: 仕様書ドラフト v1.0 final、レビュー対応一覧、改訂履歴
- レビュー観点: 実装可能性、明確性、用語統一、将来拡張の余地が保たれているか

## 依存関係
- フェーズ1で継承対象と矛盾を整理しないと、型システムと章構成を確定できない。
- フェーズ2の型システムが固まらないと、フェーズ3の構文とフェーズ4の意味論がぶれる。
- フェーズ4の実行モデルが定まらないと、judge、accept、fallback の仕様が確定できない。
- フェーズ5の受理条件が定まらないと、標準ライブラリ境界とユースケース例が不安定になる。
- フェーズ6で API 境界を定めた後でないと、仕様書ドラフトの統合品質が上がらない。

## レビュー方針
- 概念レビュー: Kriteia の中心思想が一貫しているかを確認する。
- 仕様整合性レビュー: 型、構文、意味論、標準ライブラリが矛盾なく接続されているかを確認する。
- 用語統一レビュー: prompt、evidence、policy、accepted などの用語が章ごとに揺れていないかを見る。
- 実装可能性レビュー: 言語処理系実装者が仕様書から処理系を起こせる粒度かを確認する。
- 将来拡張レビュー: 非スコープ化した項目が後続版で拡張可能な形で残っているかを確認する。

レビュー担当ロールは次のように固定する。
- 言語設計レビュー担当: 概念境界、章責務、非スコープの逸脱を確認する。
- 型理論レビュー担当: 型形成規則、型推論、effect type の妥当性を確認する。
- 処理系レビュー担当: grammar、semantics、error model の実装可能性を確認する。
- 応用設計レビュー担当: judge、accept、監査可能性、ユースケース妥当性を確認する。

## 完了条件
- 用語集、継承一覧、不足論点テーブルが整備されている。
- 型システム、構文、実行モデル、judge、accept、エラーモデルに対して章草案がそろっている。
- 仕様書の章構成と各章の責務が確定している。
- 未解決論点が open issues として分離され、v1.0 範囲外が明記されている。
- 少なくとも 1 回の概念レビューと 1 回の実装可能性レビューを通過している。
- 別担当者が Plans と仕様草案を読めば執筆を継続できる状態になっている。
- decision log に主要判断の採用理由と棄却理由が記録されている。
- review log に指摘事項と反映状況が追跡可能な形で残っている。

| Noesis と Anchor の概念矛盾が大きい | コア概念と章構成がぶれる | フェーズ1で矛盾リストを作成し、統合案か保留かを都度明示する |
| semantic type が複雑化しすぎる | 型システム章が停滞し、実装可能性が落ちる | 第1版では必要最小限の型規則に絞り、拡張規則は将来版へ送る |
| branch と checkpoint の意味論が重い | 実行モデル章とエラーモデル章に遅延が波及する | フェーズ4で最小実用モデルを先に固定し、特殊ケースは open issues に切り出す |
| 標準ライブラリ範囲が膨張する | 仕様書の完成が遅れる | 第1版に含める judge、retriever、utility を最小限に制限する |

| 非スコープ項目へ議論が逸脱する | 策定工程が伸びる | 各フェーズで非スコープ項目を明示し、open issues へ退避する |
