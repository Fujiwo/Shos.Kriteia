# Kriteia 仕様書策定計画

## 概要
- Kriteia の既存資料を統合し、正式な仕様書へ落とし込むための策定計画を定義する。
- 仕様書本文ではなく、仕様化の順序、論点、成果物、レビュー方針を明示する。
- Noesis の探索能力と Anchor 系の根拠・受理モデルを、Kriteia の一貫した仕様として整理する。
- 既存資料で確定済みの事項と、仕様書レベルでは未確定な事項を分離する。
- 別担当者がそのまま着手できる粒度で、フェーズ単位の実行計画を示す。

## 目的

Kriteia の仕様書を、構想メモや比較資料ではなく、実装者・設計者・レビュアーが共有できる正式文書として策定するための計画を定める。既存資料を再利用しつつ、構文、型システム、実行モデル、受理条件、エラーモデル、標準ライブラリ範囲など、仕様書で確定すべき事項を段階的に整理する。

## スコープ

- Kriteia の中核概念の定義: prompt、claimset、evidence、branch、judge、accept、policy
- 四段階実行モデルの仕様化: Plan、Explore、Ground、Accept
- 型システムの仕様化: semantic type、accepted 型、制約と受理条件の関係
- 文法・構文の仕様化: 主要構文、予約語、基本構文規則
- 実行モデルとエラーモデルの仕様化
- 第1版の標準ライブラリ範囲の策定
- 仕様書の章構成、レビュー方針、完了条件の定義

## 非スコープ

- 特定 LLM ベンダーや API への実装依存仕様
- 実際のコンパイラ、REPL、LSP、デバッガの実装詳細
- FFI や他言語相互運用の詳細設計
- 分散マルチエージェント実行の完全仕様
- 高度な最適化、JIT、性能チューニングの詳細
- 第2版以降で扱う拡張 judge、拡張 retriever、プラグイン機構の詳細

## 既存資料から継承できる内容
### 概念
- Kriteia の中心概念として prompt、claimset、evidence、branch、judge、accept を継承できる。
- 四段階ライフサイクル Plan、Explore、Ground、Accept は Kriteia 本体資料から継承できる。
- Noesis 由来の探索と制約生成、Anchor 由来の根拠と受理の観点は統合対象として継承できる。

### 用語
- candidate、grounded、accepted、policy、evidence graph などの主要語彙は継承可能。
- 要確認: semantic type と accepted 型の正式な日本語訳と英語表記の統一。

### 実行モデル
- 四段階実行モデルは継承できる。
- Meaning-Typed IR と Evidence Graph IR の二重構造も継承できる。
- 要確認: branch の評価戦略、judge の合成規則、rollback の粒度は未確定。

### 型システム
- semantic type を中心に据える方向性は継承できる。
- accepted 型で受理済み成果物を区別する方針も継承できる。
- 要確認: 型の構文、部分型関係、generics の有無、policy 制約の型への統合方法。

### AI ワークフロー
- prompt 生成、候補探索、根拠収集、検証、受理の一連の流れは継承できる。
- 高説明責任 RAG、AI コードレビュー、法務・医療・金融向けのユースケースはサンプル章の材料として利用できる。

## 不足している論点
| 論点 | 現状 | 仕様化で決めること | 優先度 |
|---|---|---|---|
| 構文の完全定義 | コード例中心で BNF がない | 完全な EBNF、予約語、優先順位を定義する | 高 |
| semantic type の形式化 | 概念説明に留まる | 型形成規則、型検査規則、制約の扱いを決める | 高 |
| accepted 型の扱い | 発想はあるが形式不明 | 型記法、昇格条件、他型との関係を定義する | 高 |
| branch の評価戦略 | 探索概念のみ | 幅、深さ、枝刈り、スコアリングを定義する | 高 |
| judge の合成 | 単体 judge のイメージ中心 | 複数 judge の順序、失敗時挙動、戻り値を決める | 高 |
| policy と metric の意味論 | 用語が並列に出る | 型上の位置づけ、評価結果型、失敗条件を定義する | 高 |
| checkpoint と rollback | 概念的説明のみ | 状態粒度、副作用制約、復元範囲を決める | 中 |
| evidence graph の永続化 | 言及不足 | 監査用保存形式の必要性を整理する | 中 |
| 標準ライブラリ範囲 | 断片的 | 第1版に含める judge、retriever、utility を絞る | 中 |
| エラーモデル | 体系化されていない | compile-time、runtime、judge failure の分類を決める | 高 |
| ツールチェーン | ほぼ未定義 | 第1版で仕様対象外とする範囲を明示する | 低 |
| 他言語相互運用 | 将来構想のみ | 非スコープ化するか最低限の記述を置くか決める | 低 |

## 仕様策定フェーズ
### フェーズ1: 既存資料の統合と論点抽出
- 入力: Kriteia 本体仕様、Kriteia 比較総覧、Noesis、追加の AI ネイティブ言語アイディア、パラダイム分析レポート
- 決定事項: 継承対象、資料間の矛盾、仕様化で未確定な論点の優先順位
- 成果物: 継承一覧、不足論点テーブル、用語統一草案
- レビュー観点: 継承対象の妥当性、矛盾抽出の漏れ、優先順位の妥当性

### フェーズ2: コア概念と章構成の確定
- 入力: フェーズ1成果物
- 決定事項: 仕様書の対象読者、章立て、各章の責務、スコープと非スコープ
- 成果物: 仕様書目次案、章責務一覧、読者別想定利用シナリオ
- レビュー観点: 章構成の依存関係、読者適合性、過不足の有無

### フェーズ3: 型システムと意味論の形式化
- 入力: フェーズ2成果物、既存資料の型関連記述
- 決定事項: semantic type、accepted 型、policy と metric の型上の扱い、judge 結果の型
- 成果物: 型構文草案、型規則草案、未解決の型論点一覧
- レビュー観点: 実装可能性、理論的一貫性、既存概念との整合性

### フェーズ4: 構文と実行モデルの定義
- 入力: フェーズ3成果物、既存コード例
- 決定事項: EBNF、主要構文、四段階状態遷移、branch と checkpoint の基本動作
- 成果物: 構文草案、状態遷移図、主要構文サンプル
- レビュー観点: 曖昧さの有無、コード例との整合、説明可能性

### フェーズ5: 根拠・検証・受理の仕様化
- 入力: フェーズ4成果物、Anchor 系資料、Kriteia の judge 例
- 決定事項: claimset と evidence の構造、judge 合成規則、accept 条件、failure の扱い
- 成果物: evidence/judge/accept 章草案、失敗分類表、監査観点の整理
- レビュー観点: 受理条件の明確性、検証フローの一貫性、実務用途への適合性

### フェーズ6: 標準ライブラリ範囲と非スコープ項目の固定
- 入力: フェーズ5成果物
- 決定事項: 第1版標準ライブラリに含める judge、retriever、utility の範囲
- 成果物: 標準ライブラリ範囲表、非スコープ一覧、将来拡張メモ
- レビュー観点: スコープ肥大化の抑制、最小実用範囲の妥当性

### フェーズ7: 仕様書ドラフト統合
- 入力: フェーズ1 からフェーズ6 の成果物
- 決定事項: 章間参照、図表、用語集、整合性の最終方針
- 成果物: 仕様書ドラフト v0.1、図表一覧、用語集
- レビュー観点: 章間の一貫性、説明不足箇所、重複の有無

### フェーズ8: レビュー反映と完成条件の確認
- 入力: 仕様書ドラフト v0.1、レビュー指摘
- 決定事項: 修正反映方針、据え置く論点、v1.0 に入れる範囲
- 成果物: 仕様書ドラフト v1.0、未解決論点ログ、改訂履歴
- レビュー観点: 実装可能性、明確性、未解決事項の分離が適切か

## 依存関係
- 継承対象と矛盾の抽出が終わらないと章構成を確定できない。
- 型システムの輪郭が定まらないと構文と実行モデルの確定が不安定になる。
- branch、judge、accept の動作は実行モデルと型システムの両方に依存する。
- 標準ライブラリ範囲はコア概念とエラーモデルが固まった後でないと決めにくい。
- 比較章はコア仕様が固まった後でないと表現がぶれる。

## レビュー方針
- 概念レビュー: Kriteia の中心思想が一貫しているかを確認する。
- 仕様整合性レビュー: 型、構文、実行モデル、標準ライブラリが矛盾なく接続されているかを見る。
- 用語統一レビュー: accepted、grounded、policy、metric などの用語が章ごとに揺れていないかを確認する。
- 実装可能性レビュー: 言語処理系の実装者が仕様から処理系を起こせる粒度になっているかを確認する。
- 将来拡張レビュー: 非スコープ化した項目が後続版で拡張可能な形で残っているかを確認する。

## 完了条件
- 継承対象、未解決論点、スコープと非スコープが文書化されている。
- 仕様書の章構成と各章の責務が確定している。
- 型システム、構文、実行モデル、judge、accept、エラーモデルに対して章草案がそろっている。
- 用語集と未解決論点ログが整備されている。
- 少なくとも 1 回の概念レビューと 1 回の実装可能性レビューを通過している。
- 要確認事項が v1.0 に残る場合は、その理由と保留先が明記されている。

## リスクと対策
| リスク | 影響 | 対策 |
|---|---|---|
| Noesis と Anchor の継承境界が曖昧 | 章構成とコア概念がぶれる | フェーズ1で継承一覧を作り、Kriteia 固有要素を別列で管理する |
| semantic type の形式化が重くなりすぎる | 型システム章の策定が停滞する | 第1版では必要最小限の型規則に絞り、拡張型規則は将来版へ送る |
| branch と judge の意味論が複雑化する | 実行モデルとエラーモデルに連鎖する | 実行モデルを先に最小形で固定し、その上で judge 合成を段階追加する |
| 標準ライブラリ範囲が膨張する | 仕様書の完成が遅れる | 第1版で必須の judge と retriever に限定し、追加候補は別ログへ退避する |
| 既存資料の表現が章ごとに衝突する | 用語と記述粒度が不統一になる | 用語集と章責務表を早期に作成し、レビューで毎回照合する |
| エラーモデルが後回しになる | 実装者が処理系の失敗条件を判断できない | フェーズ5以前に失敗分類の下書きを作成して依存を前倒しする |

## 要確認事項
- policy と metric は別概念として型に載せるか、それとも共通の制約体系に統合するか。
- accepted 型は通常型に対するラッパーか、状態遷移付きの特別な型か。
- branch の評価戦略は仕様で固定するか、実装依存として抽象化するか。
- checkpoint 内で許可する副作用の範囲をどこまでに絞るか。
- evidence graph の永続化形式を第1版に含めるか。
- judge failure と runtime error をどの程度明確に分けるか。
