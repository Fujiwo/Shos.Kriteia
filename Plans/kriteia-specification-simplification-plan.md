# Kriteia 仕様簡素化計画

## 概要

- 本計画は、Kriteia の仕様を拡張するのではなく、第1版として扱う範囲を意図的に絞り込むための整理計画である。
- 簡素化の対象は、概念数、構文数、型の層、実行モデルの説明単位、標準ライブラリ範囲、将来拡張の先取り記述である。
- Kriteia の独自性である「候補生成から根拠付き受理までを一体として扱うこと」は維持する。
- 既存資料に根拠がある中核と、現時点では重いが未確定な周辺要素を分離する。
- 成果物は仕様本文ではなく、簡素化を実行するための工程計画と判断基準である。

## 簡素化の目的

Kriteia の仕様を、処理系実装者と仕様執筆者が同じ中心線で扱える最小限の形へ収束させる。ここでいう簡素化とは、概念を曖昧にすることではなく、Kriteia の独自性を保ったまま、同時に確定しようとしている論点を減らし、第1版で凍結すべきものと将来版へ送るものを明確に切り分けることである。

特に、現在の草案では次の複雑さが累積している。

- Noesis 由来の探索概念と Anchor 由来の受理概念を、広い範囲で同時に形式化しようとしている。
- 文法、型、意味論、judge、accept、stdlib、将来拡張を同じ重みで確定しようとしている。
- 実装に近い詳細と、言語の中心契約を分け切れていない箇所がある。

本計画の目的は、第1版の Kriteia を「高説明責任 AI 出力のための最小統治言語」として絞り直すことである。

## 簡素化の判断基準

- Kriteia の独自価値である「何を通してよいか」を直接支える要素は残す。
- 探索や検証を支えるが、第1版で完全形式化しなくても中心価値が保てる要素は縮小候補とする。
- 実装戦略に近く、複数の設計余地が残るものは正文から外し、提案または将来拡張へ回す。
- 複数章にまたがって同じ役割を説明している要素は統合候補とする。
- 根拠資料が薄い要素は、無理に確定せず `要確認` または将来拡張候補とする。
- 簡素化によって Kriteia が単なる AI 呼び出し DSL に見えるなら、その簡素化案は採用しない。

## 現行仕様の主要要素

現行の資料と仕様草案から見ると、Kriteia の主要要素は次のとおりである。

- コア概念: `prompt`、`claimset`、`evidence`、`branch`、`checkpoint`、`judge`、`accept`、`accepted artifact`
- 実行モデル: Plan、Explore、Ground、Accept の四段階
- 型システム: `semantic type`、`draft<T>`、`accepted<T>`、`policy`、`metric`、judge result
- ランタイム要素: Meaning-Typed IR、Evidence Graph IR、Choice Point Engine、Judge Pipeline、Acceptance Gate
- 標準機能候補: `think`、retrieve、CitationVerifier、ConsistencyCheck、PolicyChecker
- 将来拡張に近い要素: effect type、distributed branch、human-in-the-loop accept、evidence graph 永続化、完全な stdlib、versioning

このうち、中心契約と周辺実装戦略が同じ本文密度で並んでいる点が、現時点の複雑さの主因である。

## 第1版に残す中核

第1版で明示的に残すべき中核は次のとおりである。

### 1. 受理モデル

- `claimset`
- `evidence`
- `judge`
- `accept`
- `accepted artifact`

これは Kriteia が他案と異なる最短軸であり、ここを薄めると Kriteia の独自性が崩れる。

### 2. 最小探索モデル

- `prompt`
- `branch`
- Ground 前までの候補比較

ただし、第1版では Noesis 的な探索能力を完全一般形で入れるのではなく、「複数候補を比較しうる」最小意味論にとどめる方がよい。探索戦略の一般化や高度な枝刈り最適化は不要である。

### 3. 最小型区別

- draft と accepted の区別
- `policy` と `metric` の役割差

型システム全体を重くするのではなく、受理前と受理後を区別できる最小限の型契約に絞る。

### 4. 最小実行ライフサイクル

- 生成
- grounding
- judge
- accept

Plan、Explore、Ground、Accept の四段階は概念として残してよいが、第1版正文では「候補生成から受理までの順序保証」を優先し、実装寄りの内部責務分解は薄くする案が有力である。

## 統合・縮小候補

以下は第1版で統合または縮小すべき候補である。

### A. ランタイム内部要素の正文扱い

- Meaning-Typed IR
- Evidence Graph IR
- Choice Point Engine
- Constraint Synthesizer
- Judge Pipeline
- Acceptance Gate

これらは Kriteia の理解には有用だが、正文で強く凍結すると実装自由度を過剰に奪う。第1版では「概念的役割」に留め、内部構成図は参考記述へ下げる案が妥当である。

### B. 探索の一般性

- dynamic width
- 複雑な score 関数型
- nested checkpoint の詳細意味論
- 並列 branch の順序保証

これらは Kriteia の中核というより、Noesis 由来の高度化部分である。第1版では static で理解可能な最小探索へ寄せる方が簡素である。

### C. 型システムの重さ

- `semantic type` の完全形式化
- effect type
- generic type parameter の導入可否
- subtyping の広い導入

受理境界の区別を実現する最低限を残し、型理論としての一般化は後ろへ送る。

### D. 標準ライブラリの広がり

- vendor 固有モデル設定
- ドメイン特化 Retriever 群
- 完全な Verifier/Evaluator カタログ
- 監査ストレージの標準化

第1版では最小 API 境界だけを示し、充実は将来版に回す。

### E. 章構成の細分化

`judge` と `accept`、`根拠` と `grounding`、`実行モデル` と `標準ライブラリ` の境界は重要だが、分割しすぎると依存関係の追跡が重くなる。第1版では章責務を維持しつつ、本文の密度は「最小契約」と「将来拡張候補」に二層化する方がよい。

## 将来拡張へ回す候補

次の項目は、現時点では仕様簡素化のために将来版送り候補とするのが妥当である。

- effect type
- evidence graph の永続化形式
- distributed branch
- human-in-the-loop accept の厳密モデル
- policy 言語の高度化
- versioning と後方互換性の最終方針
- 完全な grammar spec
- 完全な stdlib カタログ
- ランタイム最適化と JIT 詳細

これらは重要ではあるが、現時点の Kriteia の独自価値を説明するのに必須ではない。

## 章構成への影響

簡素化を進める場合、章構成には次の影響が出る。

### 維持する章

- 導入と位置づけ
- 設計目標と問題設定
- コア概念
- 実行モデル
- 型システム
- 文法と構文
- 根拠と grounding
- judge と検証
- accept と受理ゲート
- 将来拡張と非スコープ

### 密度を下げる章

- 探索と分岐: 高度探索の一般化は薄くする。
- 標準ライブラリ: 最小 API 境界だけを扱う。
- 実装パターン: 例示は最小数に絞る。
- 関連言語との比較: 独自性確認に必要な比較だけを残す。

### 統合候補

- `prompt と生成` は `コア概念` と `文法と構文` の間に吸収できる余地がある。
- `標準ライブラリ` は独立章を維持してよいが、詳細カタログではなく「境界章」に縮小する。

### 章ごとの簡素化優先順位

1. 型システム
2. 探索と分岐
3. 標準ライブラリ
4. 文法と構文
5. 実装パターン

## 作業フェーズ

### フェーズ1: 現行仕様の簡素化対象を棚卸しする

- 入力: Documents/Kriteia言語設計詳細.md、Documents/Kriteia比較総覧.md、Specifications/01 から 16
- 決定事項: 現行仕様要素を「中核」「縮小候補」「将来拡張候補」に分類する
- 成果物: 簡素化対象一覧、削らない中核一覧、重複説明一覧
- レビュー観点: Kriteia の独自性を壊していないか、削減対象が中心概念へ食い込んでいないか

### フェーズ2: 第1版の最小コアを凍結する

- 入力: フェーズ1成果物、既存の型システム章、judge/accept 章
- 決定事項: 第1版で必須とする概念、型区別、実行順序、受理条件の最小集合
- 成果物: v1 core 定義メモ、最小概念表、簡素化方針メモ
- レビュー観点: `prompt`、`claimset`、`evidence`、`judge`、`accept` の連鎖が明瞭か

### フェーズ3: 章ごとの削減方針を決める

- 入力: フェーズ2成果物、Specifications/05、06、08、13、16
- 決定事項: どの章で詳細を削り、どこへ `要確認` または将来版送りとして移すか
- 成果物: 章別削減方針、章構成への影響一覧、移送先一覧
- レビュー観点: 情報が欠落していないか、章間依存がむしろ複雑になっていないか

### フェーズ4: 簡素化後の本文基準を定める

- 入力: フェーズ3成果物、既存の仕様ドラフト全体
- 決定事項: 正文に残す粒度、参考記述へ下げる粒度、将来拡張へ回す粒度
- 成果物: 執筆基準、節ごとの簡素化ルール、用語維持ルール
- レビュー観点: シンプル化が曖昧化や情報隠蔽になっていないか

### フェーズ5: open issues と decision log を更新する

- 入力: フェーズ4成果物、Specifications/open-issues-log.md、Specifications/decision-log.md
- 決定事項: 第1版で凍結しない項目、将来版送り理由、設計上の保留境界
- 成果物: 更新済み open issues、decision log、簡素化理由の記録
- レビュー観点: 後で戻れる記録になっているか、判断理由が欠落していないか

### フェーズ6: 仕様本文へ反映する

- 入力: フェーズ1から 5 の成果物、Specifications/01 から 16
- 決定事項: 章ごとの圧縮、参考記述への退避、重複表現の統合
- 成果物: 簡素化後の仕様ドラフト
- レビュー観点: 全体が短くなっただけでなく、中心線が明確になっているか

## リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 探索要素を削りすぎて Kriteia が Anchor に近づきすぎる | 独自性が弱く見える | `branch` と最小探索意味論は残す |
| 型を削りすぎて受理境界が曖昧になる | accept の強みが消える | draft と accepted の区別は維持する |
| ランタイム内部要素を削りすぎて実装像が見えなくなる | 実装者の足場が弱くなる | 正文からは薄めても参考記述として残す |
| stdlib を広く残しすぎて第1版が肥大化する | 仕様全体が再び重くなる | 最小 API 境界だけを正文に残す |
| 将来拡張候補を本文へ残しすぎる | 第1版の焦点がぼける | 第16章と open issues へ退避する |

## 要確認事項

- `branch` を第1版の正文中心に残すか、限定的構文として扱うか。
- Plan、Explore、Ground、Accept の四段階を正文で維持するか、より短い実行ライフサイクル記述へ圧縮するか。
- `prompt と生成` を独立章として残すか、コア概念章へ吸収するか。
- `semantic type` を第1版でどこまで定義するか。
- `think` を言語組み込みとするか、標準ライブラリ関数とするか。
