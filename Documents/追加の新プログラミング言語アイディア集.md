# 追加の新プログラミング言語アイディア集

Documents.Old 内の [新プログラミング言語の革新的アイデア3選](Documents.Old/新プログラミング言語の革新的アイデア3選.md) と [Noesis.md](Documents.Old/Noesis.md) を参照すると、既存案の主軸は「安全なシステム言語」「AIネイティブ言語」「超分散クラウド言語」にある。そこで本書では、これらと重ならない新規軸として、「時間と因果関係」「異種計算資源」「型進化と永続互換性」に焦点を当てた追加案を提示する。

## アイディア 1: Chronicle

* **キャッチコピー**: 非同期バグを再現ではなく因果で潰す、時間指向プログラミング言語
* **ターゲット層と主なユースケース**: イベント駆動システム、分散バックエンド、ストリーム処理、取引監査、ワークフロー基盤、IoT テレメトリ集約の開発者を主対象とする。特に、「再現しない障害」「順序依存の不具合」「監査証跡と実行コードの分断」に苦しむチームに向く。
* **解決する既存言語の課題**: Go、Java、TypeScript、Python は非同期コードの記述自体は可能だが、「なぜこの順序で起きたか」「どのイベントがどの結果を引き起こしたか」を型や構文で保持しない。そのため、本番障害時にはログの寄せ集めから人間が因果関係を復元しなければならない。Chronicle はイベントを単なるメッセージではなく「時刻・因果・再実行可能性を持つ第一級の値」として扱い、実行と監査を同じ言語モデルへ統合する。
* **コアとなる言語仕様とパラダイム**: パラダイムは「時間指向 + イベントソーシング + 関数型データフロー」である。実行モデルは AOT コンパイルされたコードと、決定論的イベントVMの二層構造を採る。すべての副作用は `event` として記録され、関数は「現在状態をどう変えるか」ではなく「どの因果列からどの新イベントを導くか」を宣言する。ランタイムは Lamport clock や vector clock に近い因果メタデータを自動付与し、再実行、追跡、巻き戻しを言語レベルで可能にする。
* **特徴的なシンタックスの例**:

```chronicle
stream OrderFlow {
    event OrderPlaced(order: Order)
    event PaymentCaptured(order_id: OrderId, tx: TxId)
    event InventoryReserved(order_id: OrderId)
    event OrderCompleted(order_id: OrderId)
}

causal rule complete_order in OrderFlow {
    when OrderPlaced(order)
     and PaymentCaptured(order.id, tx)
     and InventoryReserved(order.id)
    emit OrderCompleted(order.id)
}

replay from "2026-03-31T10:15:00Z" explain OrderFlow
```

この設計では、完成条件は if 文の時系列管理ではなく `causal rule` によって記述される。`replay` は単なるデバッグ機能ではなく言語仕様の一部であり、特定時点からの再実行と説明をネイティブに行える。Chronicle の強みは、イベント駆動アーキテクチャにおける「観測」と「実装」を別物にしない点にある。

## アイディア 2: Helix

* **キャッチコピー**: CPU・GPU・NPUの境界を消す、異種計算資源ネイティブ言語
* **ターゲット層と主なユースケース**: 数値計算、機械学習推論、画像処理、科学技術計算、ゲームエンジンのレンダリング補助、データ分析基盤の高速化を行う開発者向けである。Python の表現力は欲しいが、CUDA、Metal、SIMD、推論アクセラレータ向けコードを別々に書く現状に限界を感じるチームに向く。
* **解決する既存言語の課題**: Python は記述力が高いが、高性能化の段階で NumPy、CUDA、Triton、各種 DSL に分裂しやすい。C++ や Rust は性能を出せるが、CPU ベクトル化、GPU カーネル化、NPU オフロードを一つの抽象で記述しづらい。Helix は計算を「どのデバイスで動かすか」ではなく「どの形状のデータに対して、どの依存性で計算するか」として記述させ、配置先をコンパイラに選ばせる。
* **コアとなる言語仕様とパラダイム**: パラダイムは「配列指向 + ステージング + データフロー型」である。実行モデルは staged JIT コンパイルで、最初に中間表現へ落とし込み、実行時プロファイルに応じて CPU、GPU、NPU 向けへ再下流化する。型は単なる `Tensor<f32>` ではなく、shape、layout、precision、device capability を含む。コンパイラは依存グラフから fusion、tiling、vectorization、kernel extraction を行い、プログラマは手動で GPU カーネル言語へ降りなくて済む。
* **特徴的なシンタックスの例**:

```helix
tensor Image<height, width, rgb, u8>

pipeline Sobel(input: Image<h, w, rgb, u8>) -> Tensor<h, w, f16> {
    let gray = input.map(pixel => dot(pixel, [0.299, 0.587, 0.114]))
    let gx = gray.convolve(Kernel.sobel_x)
    let gy = gray.convolve(Kernel.sobel_y)
    return sqrt(gx * gx + gy * gy)
}

run Sobel(frame)
    on auto
    budget latency < 4ms
```

`on auto` は単なる実行オプションではなく、コンパイラに対して最適な資源割当を求める宣言である。Helix はアルゴリズムとデバイス割当を分離し、しかも性能制約をコードに直接書ける点が特徴的である。Mojo や CUDA のように「性能のために別方言を覚える」必要を減らすのが狙いである。

## アイディア 3: Strata

* **キャッチコピー**: 型進化を後付け作業にしない、長寿命システム向け永続言語
* **ターゲット層と主なユースケース**: 何年も運用される業務システム、SaaS バックエンド、データ基盤、金融・行政・医療のようにスキーマ変更の互換性が重要な領域を主対象とする。特に、API バージョン、DB マイグレーション、イベントスキーマ進化の整合性維持に苦しむチームに向く。
* **解決する既存言語の課題**: TypeScript、Java、C#、Python などでは、型は主に「現在のメモリ上の形」を表す。一方、実運用では「去年の JSON」「旧版の DB スキーマ」「古いイベントログ」との互換性維持が支配的な問題になる。現状は migration スクリプト、serializer、API version、ORM 設定が分断し、人間が整合性を保っている。Strata は、型を静的構造ではなく「進化履歴を持つ永続契約」として扱い、互換性を言語仕様そのもので管理する。
* **コアとなる言語仕様とパラダイム**: パラダイムは「データ中心 + 型進化指向 + 永続ストア統合型」である。実行モデルは AOT コンパイルと version-aware runtime の組み合わせを採る。型定義には `evolves` ブロックがあり、フィールド追加、名称変更、分割・統合を宣言的に記述できる。ランタイムは古いレコードやイベントを読む際に、その場で安全な射影または昇格を行う。これにより、アプリケーションコード、永続化形式、API 契約を同一の型進化モデルで扱える。
* **特徴的なシンタックスの例**:

```strata
record Customer v1 {
    name: Text
    email: Text
}

record Customer v2 evolves v1 {
    rename name -> full_name
    add loyalty_tier: Tier = Tier.Standard
}

record Customer v3 evolves v2 {
    split full_name -> first_name, last_name by Name.split
}

fn welcome(customer: Customer@v3) -> Text {
    "Welcome, " ++ customer.first_name
}
```

この例では、`Customer` は単なる現在形の型ではなく、進化系列そのものを持つ。`Customer@v3` を要求する関数に古いバージョンのデータが渡された場合、ランタイムは宣言された進化規則に従って昇格を試みる。Strata の強みは、マイグレーションを外部の運用手順ではなく、型システムの正式な一部にする点にある。

---

これら3案は、Documents.Old の Aegis、Noesis、Omnia が切り開いた「安全性」「AI」「分散インフラ」の方向とは別に、現代開発の別の痛点を狙っている。Chronicle は時間と因果を、Helix は異種計算資源の配置を、Strata は型進化と永続互換性を、それぞれ言語の第一級概念へ押し上げる。

新しさの要点は、既存言語がライブラリや外部ツールへ追い出してきた問題を、言語の中心へ引き戻していることにある。Chronicle は observability を、Helix は accelerator placement を、Strata は migration を、いずれも「後工程」ではなく「言語仕様」として扱う。この方向は、Lattice、Chord、Mosaic とも重ならず、追加のユニーク案として十分に成立する。
