# Lattice言語設計詳細

## アイディア 1: Lattice

* **キャッチコピー**: 借用を見せずに安全性を得る、段階的可変性言語
* **ターゲット層と主なユースケース**: Rustの安全性は欲しいが借用とライフタイムの学習コストを避けたいシステムプログラマ、ゲームエンジン開発者、低レイテンシなバックエンド開発者を主対象とする。特に、更新ループが明確なシミュレーション、ECS、ストリーム処理、リアルタイムデータ変換基盤に向く。
* **解決する既存言語の課題**: Rustはメモリ安全性を実現する一方で、借用規則とライフタイムの理解が導入障壁になりやすい。GoやJavaは書きやすいが、GC由来のレイテンシ揺らぎやヒープ圧力を受けやすい。C++は自由度が高い反面、所有権境界が曖昧になりやすく、大規模化すると安全性レビューのコストが跳ね上がる。Latticeは「いつ可変でよいか」を時間軸で制約し、「どこが所有者か」を開発者に細かく意識させないことで、この三者の弱点をまとめて減らす。
* **コアとなる言語仕様とパラダイム**: 値指向とデータ指向を中核に置いたハイブリッド言語であり、パラダイムとしては「値ベース命令型 + 関数型 + データ指向」を採用する。実行モデルはAOTコンパイルで、ネイティブコードを生成する。最大の特徴は「phase block」で、可変操作はこのブロック内部に限定され、ブロック外ではデータは常に凍結済みのスナップショットとして扱われる。コンパイラは phase 境界をリージョン境界として解釈し、局所的な破壊的更新を許しつつ、境界外では値として安全に扱えるよう所有権を自動推論する。さらに、反復パターンを解析して AoS と SoA を自動変換し、ECS 的な処理を普通のレコード記法で書けるようにする。
* **特徴的なシンタックスの例**:

```lattice
entity Particle {
    pos: Vec3
    vel: Vec3
    life: f32
}

phase update(world: mut World, dt: f32) {
    for particle in world.particles where particle.life > 0.0 {
        particle.pos += particle.vel * dt
        particle.life -= dt
    }
}

let next_world = commit update(world, 0.016)
render(next_world)
```

この構文では、`phase` の内部だけが可変領域であり、`commit` した時点で `next_world` は再び不変スナップショットになる。つまり、Rustのように参照の寿命を逐一追いかけなくても、「更新はこの時間帯だけ」というルールが型システムそのものになる。コンパイラ側は `world.particles` の走査が連続アクセス中心だと判定できるため、内部レイアウトを SoA 寄りに最適化しやすく、記述力と実行性能のトレードオフを小さくできる。

## 1. Latticeとは何か

Lattice は、メモリ安全性と実行性能を両立したい一方で、Rust の借用規則をそのまま受け入れるのは負担が大きい、という現実的な要求から出発する言語である。

既存言語の課題はおおむね次の三角形に整理できる。

* C++ は速いが、所有権と解放責任が人間の規律に依存しやすい。
* Go や Java は書きやすいが、GC の存在がレイテンシの予測を難しくする。
* Rust は安全だが、ライフタイムと借用の理解に継続的な認知負荷を要求する。

Lattice の発想は、この問題を「参照がどう生きるか」ではなく「いつ変更してよいか」に変換することにある。開発者が直接管理するのは細かな所有権グラフではなく、更新可能な時間帯、すなわち `phase` の境界である。

この設計により、Lattice は次の立場を取る。

* 通常のプログラム世界では値は不変スナップショットとして扱う。
* 明示された phase の内部だけ、局所的な破壊的更新を許す。
* phase が終わった瞬間、その更新結果は再び値へ凍結される。
* コンパイラはこの境界を利用して、所有権、別名禁止、メモリレイアウト最適化を自動推論する。

つまり Lattice は、「借用チェッカーをなくす」のではなく、「借用の複雑さを局所的な時間境界へ押し込む」言語である。

## 2. Latticeが解こうとする核心問題

Lattice の問題設定は単純である。現代のシステム言語は、主に次の4つの失敗パターンを抱えている。

### 2.1 安全性が局所規律に依存する

C++ では `unique_ptr` や `shared_ptr` を使っても、最終的には設計の一貫性が人間の規律に依存する。関数境界が増えるほど、所有者が誰なのか、いつ無効になるのかが見えにくくなる。

### 2.2 安全性を得ると学習コストが跳ね上がる

Rust は極めて強力だが、データ構造が少し複雑になると「なぜこれは借用できないのか」を理解するコストが大きい。特にグラフ構造、ECS、相互参照を含む処理、反復中の更新でつまずきやすい。

### 2.3 書きやすい言語は実行時コストを後ろへ送る

GC 言語は生産性が高いが、ヒープ圧力と停止時間の問題を完全には消せない。サーバやゲームループのようにフレーム時間や tail latency が重要な領域では、この予測不能性が設計制約になる。

### 2.4 性能のためにデータ指向へ寄せるとコードが崩れる

AoS と SoA の切り替え、SIMD 向けの再配置、キャッシュに優しい更新順序を手作業で管理すると、コードは急速に読みにくくなる。性能のために設計を犠牲にしやすい。

Lattice は、この4つを一つの抽象でまとめて扱う。可変性を phase に閉じ込め、値の世界と更新の世界を分けることで、安全性と最適化機会を同時に得る。

## 3. パラダイムと実行モデル

Lattice は単一パラダイムの言語ではない。中心にあるのは次の3要素の組み合わせである。

* **値ベース命令型**: 通常のコードは直感的な代入やレコード操作に近い感覚で書ける。
* **関数型**: phase の外では値は不変であり、関数はスナップショットを受け取って新しいスナップショットを返す。
* **データ指向**: 実行時ホットパスではメモリレイアウトをコンパイラが自動変換する。

実行モデルは AOT コンパイルであり、C や Rust と同様にネイティブコードを生成する。GC は標準の実行モデルには含めない。メモリ管理は以下の層で成り立つ。

* スタック配置可能な値は優先的にスタックへ置く。
* phase 単位で再利用できる作業メモリはリージョンとして確保する。
* 長寿命データは値オブジェクトとしてヒープに配置するが、その寿命は phase 境界と escape 解析で静的に最適化する。
* 一時オブジェクトは copy-on-write と in-place update のどちらが有利かをコンパイラが選ぶ。

この意味で Lattice は、メモリ管理そのものを露出するのではなく、「静的に消せるヒープ」を増やす方向の言語である。

## 4. 中核となる言語仕様

## 4.1 phase block

`phase` は Lattice の最重要構文であり、「更新が許可される時間帯」を明示する。

```lattice
phase simulate(world: mut World, dt: f32) {
    for body in world.bodies {
        body.velocity += gravity(body) * dt
        body.position += body.velocity * dt
    }
}
```

このブロックの意味は、`world` がこのスコープ内では排他的に更新可能であり、外の世界には同時に見えていない、ということである。Rust の `&mut` に似ているが、変数単位ではなく「更新区間」単位で排他を定義する点が異なる。

## 4.2 commit

`commit` は phase の結果を新たな不変値として確定する。

```lattice
let next_world = commit simulate(world, dt)
```

この時点で `next_world` は変更不能なスナップショットとなり、複数の読み取りコンテキストで安全に共有できる。つまり phase は「局所的な可変計算」、commit は「値世界への復帰」である。

## 4.3 mut と freeze

Lattice には可変な値と不変な値の二分法があるが、それは常時ではなく phase と結びつく。

```lattice
let scene = load_scene()
let mutable_scene = thaw scene

phase bake(scene: mut Scene) {
    optimize_meshes(scene)
    build_spatial_index(scene)
}

let baked = commit bake(mutable_scene)
```

`thaw` は immutable snapshot を phase 用の可変ワークセットへ変換し、`commit` で 다시 immutable へ戻す。この設計により、「全体は値、局所は更新可能」という一貫したメンタルモデルを維持できる。

## 4.4 region

phase の裏側にはリージョンメモリがある。開発者が必要に応じて明示できるが、通常はコンパイラが自動付与する。

```lattice
region frame_temp {
    phase build_commands(ctx: mut RenderContext) {
        generate_draw_calls(ctx)
    }
}
```

この `region` 内で確保した一時メモリはフレーム終了時にまとめて捨てられる。GC のような個別トレースが不要であり、リアルタイム用途に向く。

## 4.5 layout polymorphism

Lattice の革新点の一つは、ソースコード上の論理構造と実際のメモリレイアウトを切り離す点にある。

```lattice
entity Particle {
    pos: Vec3
    vel: Vec3
    color: Rgba8
    life: f32
}

layout auto ParticleSet = Array<Particle>
```

開発者は `Array<Particle>` として書くが、コンパイラはアクセスパターンに応じて AoS、SoA、AoSoA のいずれかへ変換できる。結果として、記述性を落とさずに DOD 寄りの性能を引き出せる。

## 5. 型システムの考え方

Lattice は Rust のような露骨な借用注釈を避ける代わりに、次の3層で安全性を確保する。

### 5.1 値型と phase 型

通常の値は immutable であり、複製や共有が自由である。一方、phase 内で扱う `mut T` は排他的更新が許される一時型である。

### 5.2 エスケープ制御

phase 内で生成された内部参照は phase 外へ持ち出せない。つまり、借用チェッカーを毎行露出する代わりに、「phase を越えて生きる参照は禁止」という高レベル制約へ圧縮する。

### 5.3 線形資源型

ファイルハンドル、GPU バッファ、ソケットのような資源には `resource` 型を用意し、これは複製不可で明示的に消費される。

```lattice
resource File

fn write_log(file: consume File, msg: Text) -> File {
    append(file, msg)
}
```

これにより、一般データは phase で管理し、危険な外部資源だけは線形的に厳密管理するという分業ができる。

## 6. 典型的な構文例

## 6.1 ECS 更新

```lattice
phase movement(world: mut World, dt: f32) {
    for (pos, vel) in zip(world.position, world.velocity) {
        pos += vel * dt
    }
}
```

この構文は論理的には zip だが、コンパイラは SoA と SIMD を前提に最適化できる。

## 6.2 トランザクション風更新

```lattice
phase transfer(accounts: mut Accounts, from: Id, to: Id, amount: Money) {
    accounts[from].balance -= amount
    accounts[to].balance += amount
}

let next_accounts = commit transfer(accounts, a, b, 100yen)
```

これは不変マップを都度コピーしているように見えるが、phase 内では差分更新として扱えるため、実装は in-place に近づけられる。

## 6.3 並列 phase

```lattice
parallel phase cull(scene: mut Scene) {
    for chunk in scene.chunks partitioned {
        chunk.visible = compute_visibility(chunk)
    }
}
```

`partitioned` が付く場合、コンパイラはデータ分割が独立であることを確認し、ロックなしの並列化を適用できる。Lattice は共有可変性ではなく、分割可能な phase を並列実行する。

## 7. コンパイラがやる仕事

Lattice の価値は、言語表面よりむしろコンパイラにある。コンパイラは少なくとも次を行う必要がある。

### 7.1 phase 境界解析

どの値が phase 内でだけ mutable かを決定し、外側との alias を遮断する。

### 7.2 エスケープ解析

phase 内の一時オブジェクトが外へ漏れない場合、スタック配置や region 配置へ落とす。

### 7.3 copy-on-write 除去

ソース上は immutable 値を返していても、唯一の所有者であると証明できれば in-place update へ変換する。

### 7.4 レイアウト再配置

ループ解析、ホットパス解析、SIMD 幅を見て AoS/SoA/AoSoA を選ぶ。

### 7.5 自動ベクトル化と並列化

phase が副作用境界として明確なので、ループ独立性や書き込み範囲の推論がしやすい。C++ より高級な表現から、より多くの最適化を引き出せる。

## 8. Latticeが既存言語より優れる点

## 8.1 C++より優れる点

所有権レビューと未定義動作への警戒を、型と phase 境界へ押し込める。人間の規律に頼る部分が減る。

## 8.2 Rustより優れる点

借用とライフタイムの細かな露出を避けられる。特にシミュレーションループ、ECS、パイプライン処理では、phase 単位の排他が自然である。

## 8.3 Goより優れる点

GC が前提でないため、フレーム時間や tail latency をより制御しやすい。

## 8.4 ZigやJaiより優れる点

データ指向最適化を扱いつつも、メモリ管理を露骨にプログラマへ押し付けない。安全性とレイアウト最適化の両方を言語設計の中心に置く。

## 9. Latticeの弱点とトレードオフ

Lattice にも明確な弱点がある。

* phase の境界設計が悪いと、逆にデータの移し替えが増える。
* 自己参照構造や複雑な循環グラフは、Rust ほどではないにせよ工夫が必要になる。
* コンパイラの最適化能力に依存する割合が高く、実装難易度が高い。
* 「いつ freeze されるか」が暗黙すぎると、性能予測が難しくなる可能性がある。
* 高度な layout 最適化はデバッグ時にメモリ像を分かりにくくする。

したがって Lattice は、単に構文が美しいだけでは成立しない。コンパイラの可視化機能、最適化レポート、phase ごとのコスト表示が必須になる。

## 10. 典型的なユースケース

Lattice が強いのは次のような領域である。

* ゲームエンジンのフレーム更新
* ECS ベースのシミュレーション
* 低レイテンシなイベント処理基盤
* 画像、音声、信号処理のパイプライン
* インメモリ OLAP や列指向データ変換
* 組み込みやリアルタイム寄りの制御系

逆に、単純な業務Webアプリ、強い動的性が必要なスクリプト、GC で十分な短命ツールでは、Lattice の複雑さは過剰になる可能性が高い。

## 11. 実装するとしたらどう始めるか

Lattice を本当に作るなら、最初から万能言語を目指すより、順序立てて検証するべきである。

1. 値型と `phase/commit` の最小系を設計する。
2. phase 境界の alias 解析と escape 解析を実装する。
3. リージョンメモリと stack promotion を導入する。
4. AoS から SoA への自動変換を限定ケースで入れる。
5. 並列 phase と SIMD 最適化を追加する。
6. 最後に resource 型や FFI を整備する。

この順なら、各段階で「借用を見せずに安全性を得る」という価値が本当に成立するかを測定できる。

## 12. まとめ

Lattice の核は、「可変性を値の属性ではなく、時間境界の属性として扱う」点にある。Rust が所有権を厳密に見せることで安全性を獲得したのに対し、Lattice は phase という明示的な更新区間を導入し、その内側に破壊的更新を閉じ込めることで、同じ目的へ別経路から到達しようとする。

その結果として得られるのは、次の三重の利点である。

* 開発者はライフタイムの詳細を逐一考えなくてよい。
* コンパイラは更新区間を手掛かりに aggressive な最適化をかけやすい。
* 実行時は GC なしでも予測可能なメモリ挙動を実現しやすい。

新規性は、所有権モデルを否定することではなく、それを人間が直接操作する表面言語から一段奥へ隠し、phase、commit、region、layout polymorphism というより粗い抽象へ再編成する点にある。Lattice は「安全だが難しい」か「簡単だが不安定」かという二択を崩し、「安全性をコンパイラへ戻す」方向の次世代システム言語として成立しうる。
