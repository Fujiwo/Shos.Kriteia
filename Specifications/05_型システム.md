# Kriteia 仕様書 第5章 型システム

## この章の目的

Kriteia の型システムを、第1版に必要な最小限の粒度で定義する。特に、draft と accepted の区別、`claimset` と `evidence` の位置づけ、`policy` と `metric` の役割差、`policy` の最小表現形式、`accepted<T>` の受理境界を先に固め、`semantic type` の重い形式化や effect type のような拡張論点は将来版へ送る前提を明確にする。

## この章で確定する事項

- 第1版で必要な型区別
- draft 型と accepted 型の関係
- `claimset`、`evidence`、judge result の型上の位置づけ
- `policy` と `metric` の型上の扱い
- `semantic type` の最小定義
- 第1版で扱わない型要素

## 本文草案

### 5.1 型システムの設計原則

Kriteia の型システムは、生成されたものをそのまま公開可能とみなさず、受理状態の違いを型で区別し、構造だけでなく意味と制約も型に関与させることを原則とする。これは、AI 出力を一般的な値として扱うのではなく、検証と受理を経るべき候補として扱うためである。

### 5.2 型の分類

第1版では、通常の構造型を全面的に作り替えるのではなく、Kriteia に固有の境界だけを型で区別する方針を取る。具体的には、基本型に加えて、`claimset`、`evidence`、judge result、draft 型、accepted 型、`policy` と `metric` の役割差を表せればよい。`semantic type` はこの最小集合を支える軽量な意味注釈層として扱い、独立した重い型理論としてはまだ凍結しない。ここでの `accepted<T>` は通常値の別名ではなく、`accept` を通過した値だけが入る opaque wrapper として解釈する。

### 5.3 semantic type

`semantic type` は、Kriteia の第1版では「入力や値が何として扱われるべきか」を補助的に示す最小定義に留めるのが妥当である。通常の構造型に対して、期待出力、制約候補、受理条件との結び付きといった意味情報を薄く重ねる層として扱い、独立型カテゴリとしての完全形式化や高度な推論規則は将来版へ送る。これにより、Kriteia の独自性を支えつつ、型章の複雑さを抑えられる。

### 5.4 draft 型と accepted 型

Kriteia では、生成直後の候補は `draft<T>` として扱い、judge と `accept` を通過したものだけを `accepted<T>` へ昇格させる。この区別は第1版でも外せない中核であり、Kriteia を単なる AI 呼び出し DSL にしないための最短の型契約である。第1版では `accepted<T>` を opaque wrapper として扱い、通常の構築子、キャスト、代入だけでは生成できない型とする。これにより、外部公開や副作用実行に使える値が `accept` を経たものだけであることを型上で表現できる。

### 5.5 policy と metric の型上の扱い

`policy` と `metric` は、どちらも judge や accept に関与するが、同一概念として扱わないことが第1版の簡素化において重要である。`policy` は「通してよいか」を決める条件群であり、第1版では名前付き `policy` ブロックの中に `require` 条件を列挙する最小 DSL として扱う。`metric` は候補や検証結果の補助評価値であり、受理理由を補足するために使う。第1版ではこの役割差と最小構文だけを固定し、高度な制約理論や一般式との統合は将来版へ回す。

### 5.6 claimset と evidence の型

`claimset` と `evidence` は、Kriteia における検証可能性の中心である。`claimset` は候補成果物とその主張集合を保持し、`evidence` はその主張を支える根拠を表す。第1版では、`evidence` の標準バリアントを過度に固定しすぎず、文書断片、コード行、検索結果、監査記録などを含みうる抽象型または有限バリアント集合として扱う方向が適切である。

### 5.7 型形成規則

第1版で必要なのは、完全な型理論よりも「どの境界で何を禁じるか」を明確にすることである。少なくとも `prompt` が入力と期待出力を持つこと、`claimset` と `evidence` が judge の入力側に属すること、`policy` が名前付き `require` 列として定義されること、`accept` が `draft<T>` を `accepted<T>` へ変換する唯一の操作であることは固定する必要がある。subtyping、generic type parameter、effect type のような一般化は、この最小契約を確定した後でよい。

### 5.8 型推論

型推論も第1版では保守的に扱う。構造型と基本的な入力出力対応までは推論対象としてよいが、`policy`、`metric`、accepted 型への昇格条件に関わる箇所は明示注釈を優先する方が簡素である。Kriteia の第1版で重要なのは「よく推論できること」より「受理境界を誤魔化さないこと」である。

## 型の論点整理

| 論点 | 仮の方向性 | 要確認事項 |
| --- | --- | --- |
| semantic type | 軽量な意味注釈層として扱う | 独立型カテゴリとしてどこまで立てるか |
| draft と accepted | `accepted<T>` を opaque wrapper として扱う | typestate や線形性を将来版で導入するか |
| policy | 名前付き `policy` ブロックと `require` 列で扱う | 論理合成や外部 evaluator をどこまで標準化するか |
| metric | judge 補助値として扱う | `policy` とどこまで統合するか |
| effect type | 将来版送り候補 | 第1版で完全に外すか |

## 決定メモ

- 第1版では draft / accepted の区別を最小中核として維持する。
- `semantic type` の重い形式化は将来版候補として扱う。
- 第1版の `policy` は `require` 列を持つ名前付きブロックとする。
- 第1版の `accepted<T>` は `accept` のみが生成できる opaque wrapper とする。
