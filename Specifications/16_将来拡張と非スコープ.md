# Kriteia 仕様書 第16章 将来拡張と非スコープ

## この章の目的

第1版で扱う範囲と、将来版へ送る事項を最小仕様の観点から明確に分け、仕様書の終端としてスコープ境界を固定する。特に、`semantic type` の重い形式化、ランタイム内部構成の詳細、広い stdlib 仕様のような「今は触れなくてよい複雑さ」を正文から切り離すことを重視する。

## この章で確定する事項

- 第1版の非スコープ一覧
- 将来拡張候補の整理
- 他言語案との接続余地
- 後方互換性や版管理の扱い方針の位置づけ
- 第1版で凍結しない複雑化要素の明示

## 本文草案

### 16.1 本章の役割

仕様書の終端では、将来拡張と非スコープを曖昧にしないことが重要である。非スコープとは第1版で意図的に含めない事項であり、未記述とは異なる。また、将来拡張候補は、今は確定しないが設計上の配慮が必要な項目として整理されるべきである。

### 16.2 第1版の非スコープ

策定計画に基づけば、参照実装そのもの、IDE や LSP などのツールチェーン詳細、FFI や他言語連携の完全仕様、分散マルチエージェント実行の完全設計、高度な最適化や JIT 詳細、標準ライブラリ完全版、後方互換性の最終方針、教育コンテンツは第1版の非スコープとして扱うのが妥当である。加えて、ランタイム内部モジュールの完全固定、ドメイン別 stdlib カタログ、vendor 固有生成 API 仕様、partial accept の形式化、`accepted<T>` の typestate 化も第1版では扱わない。これらは重要ではあるが、本体仕様の確立より後に置くべきである。

### 16.3 将来拡張候補

将来拡張候補としては、effect type の導入、`semantic type` の重い形式化、evidence graph の永続化形式、分散 branch の意味論、human-in-the-loop accept、policy 言語の強化、Strata 的な型進化モデルとの接続、`think` 以外を含む生成 API の拡張、partial accept の意味論、`accepted<T>` の typestate 化などが考えられる。これらは現時点で方向性は示せても、正文として凍結するには資料が不足しているか、第1版の最小仕様を超えている。

### 16.4 他案との接続余地

Kriteia は、Lattice、Chord、Mosaic などの他案と補完関係を持ちうる。たとえば、実行基盤の安全性と性能では Lattice 的発想、分散会話の将来設計では Chord 的発想、policy evaluator の表現力では Mosaic 的発想が参考になる。ただし、第1版ではこれらを直接統合する仕様までは扱わない。

### 16.5 open issues との関係

本章は、未決論点をすべて本文へ抱え込む章ではない。むしろ、`open-issues-log.md` に残す論点と、第1版で非スコープまたは将来版送りとする項目を切り分けるための章である。すでに第1版方針が決まったものは decision log へ移し、残る論点だけを open issue として保持することで、仕様書全体の境界が明確になる。

## 将来版送り候補

- effect type
- `semantic type` の重い形式化
- evidence graph 永続化形式
- distributed branch
- human-in-the-loop accept
- partial accept
- `accepted<T>` の typestate 化
- `think` 以外を含む生成 API 拡張
- versioning と後方互換性

## 決定メモ

- 第1版では `semantic type` を軽量注釈層として扱い、重い形式化は将来版候補とする。
- 第1版では `think` を最小 stdlib 関数として扱い、生成 API の拡張は将来版候補とする。
- partial accept と `accepted<T>` の typestate 化は第1版の非スコープとし、将来版候補として扱う。
