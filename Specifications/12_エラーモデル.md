## この章の目的

compile-time error、runtime error、judge failure、accept 不成立、fallback を第1版に必要な粒度で整理し、Kriteia における失敗と回復の扱いを定義する。探索失敗や受理不可を例外的事象ではなく、通常経路として扱うための最小分類を与える。

## 本文草案

### 12.1 エラーモデルの必要性

Kriteia では、失敗には複数の種類がある。構文や型の誤り、探索途中の制約違反、根拠不足、judge 不合格、accept 不成立、外部効果の失敗などをすべて同じ例外として扱うと、回復戦略が不明瞭になる。そのため、本章では失敗を分類し、どこまで自動回復できるかを整理する。

### 12.2 compile-time error

compile-time error は、構文誤り、型不整合、予約語の誤用、静的に検出できる `policy` 記法違反などを含む。ここでいう `policy` 記法違反とは、名前付き `policy` ブロックの宣言自体が不正であることを指し、`require` 条件が受理を満たさなかったこととは区別する。これらはプログラム実行前に検出されるべきであり、探索や受理以前の問題として扱う。第1版では、静的にどこまで検出可能とするかを保守的に定義するのが妥当である。

### 12.3 runtime error と judge failure

runtime error は、外部 API 失敗、retrieval 失敗、利用可能でないリソース、実行時の制約崩壊などを含む。一方、judge failure は候補が検証条件を満たさなかったことを表し、通常の runtime exception と同一視しない方がよい。Kriteia では judge failure は探索や grounding の自然な結果であり、再探索や fallback へ接続されるべきである。`policy` の `require` 条件が偽になった場合も、これは `policy` 記法の壊れではなく judge failure 側の構造化失敗として扱う。

### 12.4 accept 不成立

accept 不成立は、judge 結果、`policy` 適合性、公開前提条件に照らして候補を通せなかった状態である。これもまた、例外というより業務上の不採用に近い概念であり、runtime error と区別して表現する価値がある。第1版では accept が失敗した場合、候補は `accepted<T>` を得られず `draft<T>` のまま残る。Kriteia の失敗分類で最も重要なのは、技術的失敗と受理上の不成立を混同しないことである。

### 12.5 fallback と escalation

`fallback` は代替経路への切り替えであり、`rollback` は安全な地点への復帰であり、`escalation` は自動処理を止めて人手判断へ渡す操作である。これらは同じ「失敗後処理」に見えるが、責務は異なる。第1版では、少なくとも judge failure と accept 不成立が再探索、fallback、人手エスカレーションへ進みうること、runtime error が rollback を必要としうることを区別できれば十分である。

## 失敗分類案

- 構文・型の静的失敗
- `policy` 記法の静的失敗
- 探索中の枝失敗
- runtime 実行失敗
- grounding 不足
- judge failure
- accept 不成立

## 第1版で扱わないもの

- 失敗分類ごとの完全な診断 JSON 形式
- 監査ログ保存形式の標準化
- fallback / rollback / escalation の高度な合成規則
- 分散実行時の失敗順序保証

## 未決論点

- grounding 不足を judge failure に含めるか独立分類にするか。
- fallback を構文として必須にするか。
- 失敗分類ごとの診断フォーマットをどこまで仕様に含めるか。

## 決定メモ

- `policy` 記法違反は compile-time error とし、`policy` 不成立は judge failure または accept 不成立として扱う。
- accept に失敗した候補は `accepted<T>` を得ず、受理不可として通常回復経路へ進む。
