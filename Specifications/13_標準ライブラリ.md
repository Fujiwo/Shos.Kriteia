# Kriteia 仕様書 第13章 標準ライブラリ

## この章の目的

第1版標準ライブラリに含める最小 API 境界だけを整理し、言語組み込みと stdlib の責務分担を定義する。`think`、retrieve、judge 系機能のうち、第1版正文で本当に必要な境界だけを残し、ドメイン依存の豊富な API 群や vendor 固有設定は将来版または非スコープへ回す。

## この章で確定する事項

- 言語組み込みと stdlib の最小境界
- `think`、retrieve、judge 系 API の最小位置づけ
- Verifier、Evaluator、Retriever の最小拡張点
- policy checker の最小役割
- 第1版で非スコープとするライブラリ領域

## 本文草案

### 13.1 標準ライブラリの位置づけ

Kriteia のコア概念には、言語構文として扱うべきものと、標準ライブラリ API として扱うべきものが混在する。第1版では、この章の役割を「完全なライブラリ仕様を書くこと」ではなく、「どこまでが言語本体で、どこからが差し替え可能な API かを示すこと」に限定する。`branch` や `accept` は言語組み込みに寄せ、retrieval 実装や個別 verifier は拡張点として扱う、という境界が中心になる。

### 13.2 think と生成 API

既存資料では `think<ReviewReport>(ReviewPrompt(repo))` のような形が示されている。第1版では、`think` を候補生成の標準入口となる最小 stdlib 関数として扱う。これにより、生成入口を固定しつつ、言語構文を増やさずに済む。将来版で複数の生成 API を整理する余地は残るが、第1版正文では `think` を最小の標準入口として扱えば十分である。

### 13.3 Retriever、Verifier、Evaluator

retrieval、引用検証、整合性検証、policy 評価は、実際には差し替え可能な実装が望ましい。そのため第1版では、Retriever、Verifier、Evaluator を「最小の拡張境界」として定義するだけで十分である。完全な実装カタログやドメイン別 API 群を本文に持ち込むのではなく、どの役割を差し替え可能にしておくべきかを示すことが本章の中心になる。

### 13.4 policy checker と stdlib 境界

`PolicyChecker(ReleaseGate)` のような構文例は、policy が純粋な値であるだけでなく、標準的な checker と組み合わせて実行されることを示唆する。第1版では、policy checker の最小役割だけを残し、個別業務ルールや外部制度依存のチェック群は拡張側へ置くのが妥当である。つまり、policy evaluator の存在は正文に残すが、その豊富な派生 API は残さない。

### 13.5 非スコープ

第1版の stdlib は、すべての業務ドメイン向け retrieval や verifier を包括することを目指さない。特定ベンダー依存のモデルアダプタ、完全な監査ストレージ実装、分散マルチエージェント協調ライブラリ、完全な API カタログは非スコープとして扱うのが適切である。第1版で必要なのは網羅性ではなく、境界の明確さである。

## 標準ライブラリの最小構成案

- 候補生成入口
- 基本 Retriever
- 基本 Verifier
- 基本 Evaluator
- policy checker
- escalation 補助 API

## 第1版で扱わないもの

- vendor 固有モデル設定
- ドメイン特化 Retriever / Verifier カタログ
- 完全な監査ストレージ標準
- 分散マルチエージェント協調ライブラリ

## 未決論点

- Retriever を trait 風の拡張点とするか。
- 最小インターフェースに何個の必須操作を含めるか。

## 決定メモ

- 第1版の stdlib は最小 API 境界を示す章として扱う。
- vendor 固有や完全カタログ型の記述は非スコープへ送る。
- `think` は第1版で最小 stdlib 関数として扱う。
