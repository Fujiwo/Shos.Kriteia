# Kriteia 仕様書 第4章 実行モデル

## この章の目的

## 本文草案

### 4.1 実行モデルの全体像

Kriteia の計算は、Plan、Explore、Ground、Accept の 4 段階を通る。第1版ではこの四段階を、内部 VM の完全分解としてではなく、候補生成から受理までを読者と実装者が同じ順序で理解するための最小ライフサイクルとして扱う。各段階は前段階の成果を受け取りつつ、次段階へ渡してよい状態へ整形する責務を持つ。

### 4.2 Plan

Plan は、`prompt` と入力から候補生成の前提を整える段階である。ここでは、どの種類の候補を生成するか、どの制約候補を前提とするか、どの judge や `policy` が後続で必要になるかを整理する。第1版では、Plan を高度な探索計画器として一般化するのではなく、後続段階の入力境界を整える前処理として理解できれば十分である。

### 4.3 Explore

Explore は、候補生成、`branch` 展開、最小限のスコアリング、枝刈りを行う段階である。Noesis 由来の探索能力がもっとも現れる段階だが、第1版では高度な探索最適化よりも、複数候補を比較しつつも受理前候補に留める点を重視する。Explore の出力はまだ採用可能な成果物ではなく、後続の grounding と judge を受けるべき draft 候補である。

### 4.4 Ground

Ground は、retrieval、引用検証、`evidence` の接続を行う段階である。ここでは、候補に含まれる主張を、関連する文書断片、コード行、検索結果、監査記録などへ結びつける。Kriteia が単なる探索言語に留まらないのは、この grounding を正式な実行段階として持つ点にあり、第1版でもこの境界は維持すべきである。

### 4.5 Accept

Accept は、grounding を終えた draft 候補を judge に通し、その JudgeResult と named `policy`、`metric` を Acceptance Gate へ渡して、`accepted artifact` への昇格を決定する段階である。第1版では、Acceptance Gate の最小入力集合を `grounded draft candidate`、JudgeResult、named `policy`、`metric` の 4 つに固定する。ここで重要なのは、Accept を最後のゲートとして明示することであり、内部判定器の詳細構成を細かく凍結することではない。

### 4.6 ランタイム要素

Kriteia のランタイムには、Planner、Choice Point Engine、Constraint Synthesizer、Evidence Graph Engine、Judge Pipeline、Acceptance Gate といった要素を想定できる。ただし第1版では、これらを実装必須の内部モジュールとして固定するのではなく、Plan、Explore、Ground、Accept を支える概念的役割として扱う。本文では役割だけを残し、内部構成や最適化戦略は参考記述または将来拡張へ回す。

### 4.7 補助的制御

Kriteia では、`checkpoint`、`rollback`、`fallback`、`escalation` が補助的制御として機能する。`checkpoint` と `rollback` は安全な地点への復帰を、`fallback` は代替経路への切り替えを、`escalation` は自動処理を止めて人手判断へ渡す操作を担う。これらはエラーハンドリングだけでなく、受理不能な候補をどう扱うかという統制にも関わる。

## 第1版で扱わない実装詳細

- Planner の内部アルゴリズム
- Choice Point Engine の最適化戦略
- Constraint Synthesizer の完全形式
- Evidence Graph Engine の保存形式
- Judge Pipeline の内部合成最適化

## 状態遷移の骨子

- Plan から Explore へは、入力と制約候補が探索可能な形に整ったときに遷移する。
- Explore から Ground へは、少なくとも 1 つ以上の候補が後続検証へ進む価値を持つと判断されたときに遷移する。
- Ground から Accept へは、候補の主張と根拠の対応が一定水準まで接続され、`grounded draft candidate` として judge / accept に渡せる状態になったときに遷移する。
- 失敗時には、直近の `checkpoint` へ `rollback` するか、定義済みの `fallback` へ分岐するか、または `escalation` へ進む。

- 実行モデル章は候補生成から受理までの観測可能な順序を優先して説明する。
- Acceptance Gate の最小入力集合は `grounded draft candidate`、JudgeResult、named `policy`、`metric` とする。
